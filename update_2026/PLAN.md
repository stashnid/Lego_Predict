# План роботи над датасетом LEGO (оновлення до 2026)

Документ для команди. Описує, що саме ми збираємо, у якому порядку, хто що робить і як перевірити,
що крок зроблено. Статуси: ✅ готово · 🟡 у роботі · ⬜ не почато.

---

## 1. Навіщо цей датасет

**Дослідницьке питання:** чи можна за характеристиками набору LEGO, відомими в момент покупки,
передбачити, чи подорожчає він після зняття з виробництва?

**Гіпотези, під які збираємо дані:**

| | Гіпотеза | Метод | Що потрібно з даних |
|---|---|---|---|
| H1 | Ліцензійні набори дорожчають сильніше за неліцензійні | t-тест Велча на log(приріст) + ДІ різниці | приріст, `themeGroup` |
| H2 | Дешевші набори дорожчають у відсотках сильніше | лінійна регресія log(приріст) ~ log(каталожна ціна) | приріст, каталожна ціна |
| H3 | Модель передбачає подорожчання ≥ 1.5× краще за наївний прогноз | logit, train = зняті 2015–2019, test = зняті 2020–2023; χ² прогноз × реальність | усі ознаки + ціна через 3 роки для наборів, знятих до кінця 2023 |

**Ключові визначення (не змінюємо після початку аналізу):**

- **Дата зняття** — `dateLastAvailable` з Brickset: спершу Німеччина, якщо немає — Велика Британія, потім США.
- **Каталожна ціна** — «Cena katalogowa» на promoklocki.pl, PLN.
- **Ціна через N років** — найнижча ціна пропозиції нового набору (promoklocki) у календарному місяці,
  що настає рівно через N років після дати зняття. Тижневі значення об'єднуються в місяць мінімумом.
- **Приріст** = ціна через 3 роки / каталожна ціна. **Реальний приріст** — те саме з поправкою на інфляцію.
- **Поріг для H3:** приріст ≥ 1.5. **Горизонт:** 3 роки.

**Що означає ціна promoklocki** (перевірено на сайті 14.11.2026): найнижча ціна, за яку новий набір
можна **купити** серед інтернет-магазинів і маркетплейсів, які відстежує сайт (LEGO.com, Allegro,
Empik Marketplace, Klockowo, brixani, Rozetka…). Amazon і пропозиції з кодами знижок сайт не враховує.
Це **не** середня ціна і **не** ціна угоди.

## 3. Етапи

### Етап 0. Підготовка — ⬜ (усі, 20 хв)

1. Злити PR #2 на GitHub (Merge pull request → Confirm merge).
2. У кожного: `git clone https://github.com/stashnid/Lego_Predict.git` (або `git pull`, якщо вже є).
3. `cd Lego_Predict/update_2026` → `pip install -r requirements.txt`.
4. Перевірити: `python --version` (3.10+) і `python -c "import pandas, bs4, lxml, requests"` без помилок.

**Готово, коли:** у всіх трьох скрипти запускаються без помилок імпорту.

### Етап 1. Тест promoklocki — ⬜ (учасник A, 10 хв)

```bash
python promoklocki_update.py --limit 10 --verbose
```

**Готово, коли** для більшості з 10 наборів: `result=ok`, `points` ≥ 20 для старих наборів,
`last=` — дата у 2026, `rrp=` — число. Вивід скинути в чат команди.

**Якщо `parse_failed` у всіх** — сайт знову змінив сторінку: зупинитися, скинути вивід, парсер правиться.
Після успішного тесту видалити `data/promoklocki_history.csv` і `data/promoklocki_status.csv`
(або залишити — повний запуск просто пропустить ці 10 наборів).

### Етап 2. Оновлення дат зняття з Brickset — ⬜ (учасник B, 30 хв)

Навіщо: без цього test-вибірка H3 неповна (немає наборів, знятих у другій половині 2023).

1. Отримати безкоштовний ключ API: https://brickset.com/tools/webservices/requestkey (потрібен акаунт Brickset).
2. Скрипт `brickset_refresh.py` — ⬜ **пише Claude** (наступний PR). Він:
   - завантажує набори за роками випуску 2012–2023 (~12 запитів, по 1000 наборів на сторінку);
   - зберігає `data/brickset_2026.csv`: номер, ціни й дати `dateFirstAvailable` / `dateLastAvailable` для US/UK/CA/DE, `availability`, `themeGroup`;
   - ключ, логін і пароль бере зі змінних оточення `BRICKSET_KEY`, `BRICKSET_USER`, `BRICKSET_PASS`.
3. `common.py` бере дати зняття з нового файлу, якщо він є; інакше — зі старого.

**Готово, коли:** у `data/brickset_2026.csv` для кожного року зняття 2015–2023 є 300+ наборів
(зараз у 2023 — 136).

### Етап 3. Повний збір історії цін promoklocki — ⬜ (учасник A, ніч, ~3–4 год)

Робити **після** етапу 2, щоб список знятих наборів був актуальним.

```bash
python promoklocki_update.py --only-retired --min-year 2012
```

- Між запитами пауза 2.5–3.5 с, не запускати кілька копій одночасно.
- Можна перервати (Ctrl+C) і продовжити тією ж командою — готові сторінки пропускаються.
- Якщо скрипт зупинився з «15 failures in a row» — сайт блокує або змінився; продовжити пізніше.

**Готово, коли:** у `data/promoklocki_status.csv` ≥ 90% рядків мають `result=ok` або `no_offers`;
частка `http_error` + `parse_failed` < 5%.

### Етап 4. Інфляція — ⬜ (учасник C, 30 хв)

1. Завантажити з сайту GUS (stat.gov.pl) **місячний індекс споживчих цін (CPI) Польщі** з 2015 року.
   Беремо офіційну таблицю, нічого не перераховуємо руками.
2. Зберегти як `data/cpi_poland.csv` з двома колонками: `month` (YYYY-MM), `cpi_index`
   (будь-яка база, наприклад 2015 = 100). У README записати точну назву таблиці й дату завантаження.
3. `merge_2026.py` — ⬜ **допише Claude**: реальний приріст = приріст × CPI(місяць зняття) / CPI(місяць ціни).

**Готово, коли:** у CSV є всі місяці з 01.2015 до останнього опублікованого.

### Етап 5. BrickLink — ⬜ необов'язковий (учасник C, 1–2 год)

Потрібен, лише якщо захочемо показати, наскільки ціна пропозиції відрізняється від ціни угоди.
Інструкція — у `bricklink_prices.py` та `README.md`. Токен прив'язаний до IP, тому запускає той, хто
його створив, зі свого комп'ютера. Спершу `--limit 10 --verbose`.

**Готово, коли:** для ≥ 50% наборів вибірки є `bl_avg_new` з `bl_qty_new` ≥ 3.

### Етап 6. Об'єднання і перевірка якості — ⬜ (учасник B + Claude)

```bash
python merge_2026.py
```

Перевірки — ⬜ **допише Claude** у `merge_2026.py` (окремий звіт `data/qa_report.txt`).
Рядки **не видаляються** — проблемні отримують прапорець `qa_*`, рішення приймаємо в аналізі:

| Перевірка | Прапорець | Поріг |
|---|---|---|
| Кількість наборів за роком зняття | — (у звіті) | кожен рік 2015–2023: 300+ |
| Є ціна через 3 роки | — (у звіті) | частка за роками |
| Каталожна ціна узгоджена з німецькою RRP | `qa_rrp_mismatch` | PLN / EUR поза межами 3.5–5.5 |
| Дуже великий приріст | `qa_growth_outlier` | приріст > 10 |
| Дуже низька ціна після зняття | `qa_price_low` | приріст < 0.3 |
| Мало точок історії | `qa_sparse_history` | < 6 місяців з пропозиціями |
| Дублікати номерів наборів | — (у звіті) | 0 |

**Готово, коли:** `qa_report.txt` переглянули всі троє і погодили, які прапорці виключаємо з аналізу
(рішення записуємо в розділ «Фільтри» цього файлу **до** розрахунку гіпотез).

### Етап 7. Заморозка датасету — ⬜ (учасник B, 15 хв)

1. Закомітити `data/lego_2026_merged.csv`, `qa_report.txt`, статусні файли. Перевірити, що жоден файл
   не більший за 100 МБ (ліміт GitHub). Ключі API **не комітити**.
2. Поставити git-тег `dataset-v1`. Після цього датасет не змінюємо; якщо доведеться — `dataset-v2`
   з поясненням, що змінилось.
3. Заповнити розділ «Словник даних» нижче фактичними числами (скільки наборів, період).

## 6. Ризики і запасні варіанти

| Ризик | Що робимо |
|---|---|
| promoklocki блокує запити | Збільшити `--delay` до 5; збирати частинами в різні дні |
| Сайт знову змінив сторінку | Тест на 10 наборах це покаже; виправляємо парсер до повного збору |
| Не вийшло отримати ключ Brickset | H3 рахуємо з test = зняті 2020–06.2023 і пишемо про це в обмеженнях |

## 8. Словник даних (`data/lego_2026_merged.csv`, один рядок = один набір)

| Колонка | Джерело | Опис |
|---|---|---|
| `set_no` | Brickset | номер-варіант, напр. `21322-1` |

| `pl_rrp`, `pl_rrp_source` | promoklocki | каталожна ціна, PLN, і звідки взята |
